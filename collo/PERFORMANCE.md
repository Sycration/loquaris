# Performance notes

## Measuring

```sh
cargo run --release --example bench -- bench 10       # timings over texts/
cargo run --release --example bench -- dump out.txt   # full deterministic output
```

The `dump` output covers every analysis (with and without the extension
lexicon, with and without sentence-start handling), the tags, scansion with two
option sets, inflection, and morphology lookups over the whole `texts/` corpus.
Every optimization below was checked to produce a byte-identical dump against
the unoptimized version.

## Results

Best of 5 runs on a loaded machine. Absolute numbers vary between runs, but the
ratios held across repeated interleaved runs.

| workload (whole corpus)      | before   | after   | speed-up |
|------------------------------|---------:|--------:|---------:|
| `analyze` (12.7k words)      |   68 ms  |  24 ms  |  ~2.8×   |
| `tag_text`                   | 1146 ms  |  87 ms  |  ~13×    |
| `scan_text`                  |  453 ms  | 190 ms  |  ~2.4×   |
| `inflect` (205 lemmas)       |   42 ms  | 1.8 ms  |  ~23×    |
| process start-up (load only) |   16 ms  | 9.8 ms  |  ~1.6×   |
| start-up RSS                 |   54 MB  |  38 MB  |          |

## What changed

* **Tagging.** The Viterbi search used to clone each path's full history for
  every candidate, which is quadratic in sentence length, and it built a
  `format!` string for every trigram lookup. Histories are now back-pointers
  in an arena. The original tie-break compared whole histories; that is now
  done exactly with per-step lexicographic ranks. Trigram counts come from a
  dense table indexed by tag number and generated at build time. Tag
  fractions, per-morphology tag components, and per-lemma part-of-speech masks
  are also precomputed at build time. The Roman-numeral check used to scan all
  82k lemmas linearly; it is now a binary search over a key index.
* **Analysis.** Stem and ending keys are looked up through static
  open-addressing hash indexes generated by `build.rs`, instead of binary
  searching 167k and 9.7k strings. Splits whose ending is longer than any
  known ending are skipped, and so are stem lookups when the ending does not
  exist. Model comparisons use integer IDs instead of strings. The per-stem
  `v` / `āe` / `ōe` counts are precomputed, so lowercasing no longer allocates
  in the inner loop.
* **Inflection.** Stems are indexed by lemma and endings by model, replacing
  full-table scans.
* **Scansion.** Character classes use `match` instead of `str::contains`. The
  per-character `normalize` allocations, the duplicate syllabification in
  accent selection, and the per-boundary vectors are all gone.
* **Memoization.** `tag_text` and `scan_text*` analyze each distinct
  (word, sentence-start) pair once per call. Results are pure functions of
  those inputs.
* **Data layout.** The stem and ending strings live in one blob and table
  entries store offsets. This removes ~355k load-time relocations and
  shrinks those entries about 3×.
* **New API.** `collo::find_lemma(key, extension)` is a binary-search
  replacement for `lemmas().iter().find(..)`.

`ANALYSIS_CACHE_FINGERPRINT` changes because it hashes the generated data and
`lib.rs`. Results are identical, but persisted caches will be rebuilt once.

## Possible further gains that need `unsafe` (not implemented)

All of the following rely on invariants that `build.rs` already guarantees.
Each would mostly remove bounds or UTF-8 boundary checks, so expect gains of a
few percent, not multiples.

1. **`Text::get` (`src/lib.rs`).** Replace `&TEXT[start..end]` with
   `TEXT.get_unchecked(start..end)`. Offsets are generated from the same blob,
   so they are always in range and on character boundaries. This is the
   hottest accessor: every hash probe and every stem/ending match calls it.
2. **`lookup` (`src/lib.rs`).** Use `get_unchecked` for `index[slot]` and
   `entries[position..]`. Slots are masked to the table size, and positions
   are generated from the entry table.
3. **Trigram table (`src/tagging.rs`, `ngram`).** Store the table as a 4-byte
   aligned byte array and reinterpret it as `&[u32]` (`slice::align_to`),
   indexing with `get_unchecked`. Today each lookup is a checked
   `get(i..i + 4)` plus `u32::from_le_bytes`.
4. **Tag strings.** Use `str::from_utf8_unchecked` when turning the internal
   ASCII `[u8; 3]` tags into `String`s, and in the abbreviation branch.

## Possible further gains that need API changes (no `unsafe` required)

* **`Lemma` fields as `&'static str`.** These account for ~820k of the
  remaining load-time relocations, which dominate the remaining ~10 ms
  start-up time and ~38 MB RSS. Storing offsets and exposing accessor methods
  (`lemma.key()`, …) would remove nearly all of them. This breaks code that
  reads the fields directly, such as `loquaris`.
* **`Analysis::form` / `suffix` as `String`.** Every analysis allocates. A
  borrowed or interned representation would avoid this, but it changes the
  public type.
* **A process-wide analysis cache.** A `Mutex<HashMap>` or thread-local cache
  shared across `analyze` calls would make repeated words nearly free, at the
  cost of unbounded memory growth. The app already keeps its own cache.
